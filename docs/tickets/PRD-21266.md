## Requirement understanding

One line: Monitor network devices, sites, and alerts across Ubiquiti UniFi deployments.

The requester (Ken Lee) wants the Agent platform to be able to watch a
customer's Ubiquiti UniFi network: what devices exist, what sites they
belong to, and what is currently wrong (alerts). The ticket description is
two lines plus a reference link to a third-party product page
(`conduit.wyre.ai/plugins/unifi`) that advertises the same three
capabilities as inspiration, not as a spec to copy — it is not Ubiquiti's
own documentation and is treated only as a pointer to what "done" should
feel like from a user's perspective.

## Current state (every claim carries path:line)

**This is not a new connector.** `MSPbotsAIFramework/unifi-network-mcp`
already exists, was built for [PRD-17725](https://app.clickup.com/t/PRD-17725),
and already ships 8 working tools against Ubiquiti's official UniFi Network
API, reached through Ubiquiti's own cloud connector (`api.ui.com`):

| Tool | Covers |
|---|---|
| `unifi_list_hosts` | discover consoles | README.md:128 |
| `unifi_list_sites` | **sites** | README.md:129, src/unifi_network_mcp/tools/sites.py |
| `unifi_list_devices`, `unifi_get_device`, `unifi_get_device_statistics`, `unifi_restart_device` | **network devices** | README.md:130-133, src/unifi_network_mcp/tools/devices.py:41-141 |
| `unifi_list_clients`, `unifi_get_client` | connected clients | README.md:134-135, src/unifi_network_mcp/tools/clients.py |

So two of the ticket's three nouns — "devices" and "sites" — are already
fully covered. The gap is the third: **alerts**. No tool, no endpoint call,
and no field named alert/alarm/notification exists anywhere in this repo
(confirmed: `grep -ril "alert\|alarm" src/` at 6696d66 returns nothing).

**There is no separate pre-existing repo for this ticket to reuse.** A
repo named `unifi-access-mcp` also exists in MSPbotsAIFramework, but it is
a different Ubiquiti product line — **UniFi Access** (door/physical access
control), built empty for a different ticket (PRD-18940,
`unifi-access-mcp@main` 6f6da6c, README.md:1-4: "Status: empty scaffold —
nothing is implemented yet"). It does not overlap with UniFi Network and
is not touched by this design.

**Why "alerts" is the actual gap, not just an unwrapped endpoint.**
Checked both of Ubiquiti's officially published REST specs that this
server already depends on, specifically for an alert/alarm resource:

- UniFi Site Manager API v1.0.0 (`developer.ui.com/site-manager/v1.0.0/openapi.json`,
  fetched 2026-10-30): paths are `/v1/hosts`, `/v1/hosts/{id}`, `/v1/sites`,
  `/v1/devices`, `/v1/isp-metrics/{type}`, `/v1/isp-metrics/{type}/query`,
  `/v1/sd-wan-configs*`, `/v1/connector/consoles/{id}/*path`. Zero
  occurrences of "alert" or "alarm" anywhere in the spec text.
- UniFi Network (Integration) API v11.0.97 (`developer.ui.com/network/v11.0.97/openapi.json`,
  fetched 2026-10-30 — same API family as the v10.0.162 spec this repo's
  `devices.py:1-14` docstring already cites, reached through the connector
  at `/v1/connector/consoles/{id}/network/integration/...`, i.e. exactly
  what `api_client.py:107` calls): ~60 paths covering devices, clients,
  firewall, VPN, WiFi, DNS, hotspot, switching — zero occurrences of
  "alert" or "alarm".

So there is no first-class "alerts" resource in the public API surface
this project is built on and deliberately restricted to (see
`README.md:91-104`, "Why the connector path, not a direct connection" —
the legacy local-controller alarm endpoint, `/api/s/{site}/stat/alarm`,
is session/cookie-based and not part of either official spec above; this
server never talks to a console directly). This is a genuine gap in
Ubiquiti's own documented API, not a missing wrapper around an existing
one.

**What the API does expose that is usable as a substitute.** The device
list endpoint this server already calls (`GET /v1/sites/{siteId}/devices`,
`devices.py:61-64`) returns, per the official schema
(`components.schemas["Adopted device overview"]` in the v11.0.97 spec), a
`state` enum — `ONLINE`, `OFFLINE`, `PENDING_ADOPTION`, `UPDATING`,
`GETTING_READY`, `ADOPTING`, `DELETING`, `CONNECTION_INTERRUPTED`,
`ISOLATED`, `U5G_INCORRECT_TOPOLOGY` — and a `firmwareUpdatable` boolean.
Both are real, documented, already-returned fields; nothing here is
invented.

hits in `MSPbotsAI/mbagent-wiki`'s `ProductDocs/`. There is no
`docs.mspbots.ai` connector page for either UniFi repo yet (expected: this

## Product design

### Goals / Non-goals

**Goals**: give an agent one read-only tool to see "what is currently
wrong" with the devices on a UniFi site — offline/interrupted/isolated
devices, devices stuck mid-adoption/mid-update/mid-deletion, and devices
with a firmware update available — using data this server already has
access to.

**Non-goals** (out of scope for this ticket):
- No push/webhook/streaming alerting — this is a pull tool like every
  other tool in this server.
- No acknowledge/snooze/resolve workflow — there is no backing API for
  alert state, so there is nothing to mutate.
- No ISP/WAN uptime metrics (`/v1/isp-metrics`) — that is a different,
  account-wide Site Manager resource, not scoped to one console the way
  this server's per-request `X-Unifi-Console-Id` model is; pulling it in
  would need a second, differently-shaped credential and base URL. Left
  for a future ticket if a real need shows up.
- No alert history/timeline — the API exposes current device state only,
  not a log of past transitions.
- No new write actions.

### Acceptance criteria AC1..ACn

- **AC1**: Given a site with devices in a mix of states (e.g. one
  `ONLINE`, one `OFFLINE`, one `UPDATING`), When `unifi_list_device_issues`
  is called with that `site_id`, Then only the non-`ONLINE` devices are
  returned, each tagged with which condition(s) triggered it (e.g.
  `offline`, `transitioning`), and the `ONLINE` device is excluded.
- **AC2**: Given a site where every device is `ONLINE` and
  `firmwareUpdatable` is false for all of them, When
  `unifi_list_device_issues` is called, Then it returns an empty issues
  list (not an error, not a 404).
- **AC3**: Given an invalid or unknown `site_id`, When
  `unifi_list_device_issues` is called, Then it returns the same
  structured error envelope the existing tools return for a bad site
  (`not_found` / `invalid_argument`), not a raw exception/stack trace.
- **AC4**: Given the required gateway headers (`X-Unifi-Api-Key` /
  `X-Unifi-Console-Id`) are missing on the request, When
  `unifi_list_device_issues` is called, Then it returns the same
  `NO_TOKEN` structured error every other tool in this server returns —
  not a different message or shape.
- **AC5**: Given a site with more devices than fit on one upstream page
  (upstream default page size is 25, max 200), When
  `unifi_list_device_issues` is called, Then issues from devices beyond
  the first page are still surfaced, up to a documented cap, and the
  response states whether the scan was truncated — no silent gap.
- **AC6** (isolation, required by the test-case quality bar): Given two
  different callers present two different `X-Unifi-Api-Key` /
  `X-Unifi-Console-Id` header pairs and call `unifi_list_device_issues`
  concurrently, Then neither caller's result contains a device belonging
  to the other caller's console — exercised at the credential/header
  level (same pattern as `tests/test_middleware.py`), not just asserted
  from documentation.

### Open questions

- [不阻塞 / does not block implementation] Whether "alerts" should
  eventually also cover WAN/ISP-level outages (`/v1/isp-metrics`) is left
  open — see Non-goals above. If a real need shows up, it is a separate,
  differently-scoped tool (different base URL/credential shape), not an
  extension of `unifi_list_device_issues`.
- [已假设 / explicit assumption] There was nobody to ask (vendor-mcp,
  new/ambiguous scope, no requester comment thread) about how to interpret
  "alerts" given that Ubiquiti's own API has no alert resource. This
  design assumes the device-health interpretation above. The full
  reasoning and rejected alternatives are recorded under Tech design §3
  and in the separate `[DESIGN DECISIONS]` comment
  (`references/mcp-track.md` §2.4). If this assumption is wrong, move the
  ticket back to `5b - ready for groom` with the corrected interpretation.

## Tech design

### Conclusion

Add one new read-only MCP tool, `unifi_list_device_issues`, in a new file
`src/unifi_network_mcp/tools/alerts.py`, registered in `server.py`
alongside the four existing tool modules. It reuses the exact same
upstream call `unifi_list_devices` already makes
(`GET /v1/sites/{siteId}/devices`), paginates internally up to a cap, and
filters + tags the results client-side by `state` / `firmwareUpdatable`.
No new upstream endpoint, no new credential, no new header, no new
third-party dependency.

### Where the current implementation lives

- `src/unifi_network_mcp/tools/devices.py:41-67` — `unifi_list_devices`:
  the exact endpoint and param shape (`site_id`, `offset`, `limit`,
  `filter_expr`) to reuse for the paginated scan.
- `src/unifi_network_mcp/api_client.py:91-173` — `UniFiClient`: has
  `.get(path, params)`; raises `UniFiError`, which has `.to_envelope()`.
  No new client method is needed.
- `src/unifi_network_mcp/tools/_common.py:1-5` — `NO_TOKEN`, the shared
  error returned when `client_factory()` returns `None`.
- `src/unifi_network_mcp/_json.py` — `dump_json_capped`, `error_envelope`:
  reuse both, do not reinvent serialization or the error shape.
- `src/unifi_network_mcp/server.py:120-139` — `create_mcp_server`: the
  tool-module import/register list and the `instructions` string surfaced
  to the MCP client; both need one more line.
- `README.md:122-136` — the Tools table and "When would you use this"
  section.
- Schema evidence: `components.schemas["Adopted device overview"]` in
  `developer.ui.com/network/v11.0.97/openapi.json` (fetched 2026-10-30;
  mirrors the v10.0.162 family already cited in `devices.py:1-14`) —
  `state` enum and `firmwareUpdatable` boolean.

### Data & API contract

**Input**: `site_id` (string, required — same as `unifi_list_devices`).
`max_devices` (integer, optional, default 500) — an internal scan cap, not
forwarded upstream verbatim (upstream `limit` max is 200 per the spec,
already documented in this repo's own Known Gaps pagination note,
`README.md:298-301`).

**Upstream call(s)**: one or more
`GET /v1/sites/{site_id}/devices?offset=<n>&limit=200` calls (the exact
endpoint `unifi_list_devices` already calls), looped with increasing
`offset` until either `totalCount` is covered or `max_devices` devices
have been scanned — whichever comes first.

**Output** (JSON string via `dump_json_capped`, same envelope style as
every other tool):

```json
{
  "site_id": "<site uuid>",
  "issues": [
    {
      "device_id": "F4E2C6C23F13",
      "name": "Office AP",
      "model": "U6-Pro",
      "mac": "F4E2C6C23F13",
      "state": "OFFLINE",
      "firmware_updatable": false,
      "issue_types": ["offline"]
    }
  ],
  "scanned": 42,
  "total_count": 42,
  "truncated": false
}
```

`issue_types` values (a device can carry more than one):
- `"offline"` — `state` in `{OFFLINE, CONNECTION_INTERRUPTED, ISOLATED}`
- `"transitioning"` — `state` in `{PENDING_ADOPTION, UPDATING, GETTING_READY, ADOPTING, DELETING}`
- `"topology_warning"` — `state == U5G_INCORRECT_TOPOLOGY`
- `"firmware_update_available"` — `firmwareUpdatable == true`

**Errors**: reuse `UniFiError.to_envelope()` for upstream failures — same
codes `unifi_list_devices` already returns (`invalid_argument` / 401 /
404 / `rate_limited` / `upstream_error`, see `api_client.py:61-77`);
`NO_TOKEN` when gateway headers are missing. No new error shape.

**Backward compatibility**: purely additive. New file, one new import +
one new `register()` call + one new sentence in `server.py`'s
`instructions` string. No existing tool's signature, parameters, or
output shape changes.

### Key flow / sequence

1. Gateway middleware (`server.py`'s `GatewayTokenMiddleware`, unchanged)
   puts the caller's `X-Unifi-Api-Key` / `X-Unifi-Console-Id` into the
   per-request contextvar.
2. Agent calls `unifi_list_device_issues(site_id)`.
3. Tool resolves a `UniFiClient` via the unchanged `client_factory()`;
   returns `NO_TOKEN` if there is none (AC4).
4. Tool loops `client.get(f"/v1/sites/{site_id}/devices", params={"offset": o, "limit": 200})`
   until all devices are scanned or `max_devices` is reached (AC5).
5. Tool filters the combined device list client-side by `state` /
   `firmwareUpdatable`, building `issue_types` per device (AC1, AC2).
6. Tool returns `dump_json_capped({...})`. Any `UniFiError` raised in step
   4 is converted via `.to_envelope()` (AC3).

### Non-functional

- **Idempotency & concurrency**: read-only (GET only); safe to call
  repeatedly or concurrently. Introduces no new shared mutable state
  beyond the existing shared `httpx.AsyncClient` connection pool
  (`api_client.py:49`), which is already documented as credential-free
  and safe to share across requests.
- **Performance**: worst case `ceil(total_count / 200)` upstream calls per
  invocation, bounded by `max_devices` (default 500 → at most 3 calls),
  so one tool call cannot fan out unboundedly against a very large fleet.
  Same per-console rate limit (100 req/min, per the connector's own
  documented limit) applies as every other tool in this server.
- **Security**: no new credential, no new header, no new upstream host —
  the connector path is unchanged (Ubiquiti's own `api.ui.com` proxy, no
  direct console exposure). Response size is still bounded by
  `dump_json_capped`'s existing cap.
- **Multi-tenant isolation**: identical mechanism to every other tool —
  the contextvar + one-`UniFiClient`-per-request pattern (`server.py`)
  means two concurrent callers with different `X-Unifi-Console-Id`
  headers can never see each other's devices, because the console ID is
  baked into `UniFiClient._base_url` at construction
  (`api_client.py:105-107`) and never shared across requests. This new
  tool introduces no new state that could leak across tenants (AC6).
- **Observability**: errors flow through the same `UniFiError` /
  `error_envelope` path already used (and already logged/returned) by
  every other tool; no new logging requirement.

### Rollout & rollback

Single-repo, additive change to a stateless Streamable-HTTP MCP server
with no persistent storage and no migration. No feature flag needed — it
is a new, independently-callable tool; every existing tool and its
contract is untouched. Ship = merge `dev/PRD-21266` to `main` (review leg,
per `references/mcp-track.md` §4.4), then publish to INT. Rollback =

### Test strategy

Unit tests in `tests/test_tools.py`, mocking `UniFiClient.get` — mirror
the existing per-tool test pattern already in that file — covering AC1,
AC2, AC3, AC5. AC4 (missing headers) is a one-line assertion matching the
existing `NO_TOKEN` tests for other tools, if present, or a new minimal
one following the same shape. AC6 (cross-tenant isolation) extends the
existing concurrent-context test already in `tests/test_middleware.py`

No real vendor account exists for this repo (same as the original
PRD-17725 build — see `README.md:213-221` Known Gaps), so there is no
live-console verification for this ticket either; note results as "needs

**Regression surface**: none expected on the four existing tool modules —
this is a new file and three additive lines in `server.py`. The one
genuine regression risk is `server.py`'s `instructions` string getting
long enough to matter for context budget; not a concern at one more
sentence.

0.5–1 day. Single sub-task: implement `alerts.py`, wire it into

- **Risk**: the device `state` enum or `firmwareUpdatable` field could
  behave differently on a real controller than the spec documents — every
  existing tool in this repo already carries the same "desk-verified, not
  field-verified" caveat (`README.md:213-310`, Known Gaps). Mitigate by
  keeping the same honest disclosure pattern in this tool's docstring and
  in Known Gaps, not by blocking this ticket on acquiring a real account.
- **Dependency**: none on other tickets. This is a pure vendor-repo
  change; no gateway or control-plane change is needed (confirmed: no new
  credential type, no new registration fields — `unifi-network-mcp` is
  already registered for INT).
